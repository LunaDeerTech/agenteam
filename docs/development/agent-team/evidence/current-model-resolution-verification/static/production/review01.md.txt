## P1：原 writer 屏障后仍可交付锁前的陈旧配置错误

定位：`resolver.go:97–115,157–174`。Discover 在 Tx 外读取 preparation、phase 与配置并缓存 readErr；preflight 获得原 Command EX 后只有当前 consumer Validate，没有重读 preparation。随后直接返回原 readErr 或做原 row 的 semantic 判断。

静态可达时序：同单位已有 prepared；旧 final writer 正在将其完成，另一个 Discover 先读到旧 prepared；旧 writer 提交，合法配置修改将原 live Model/Provider 禁用或删除；该 Discover 的候选读取记下 INVALID_STATE/NOT_FOUND。它随后取得原 writer 锁并完成当前授权，却在 170–171 行交付陈旧错误，未发现同单位已经 committed 的不可变结果。普通真实 Tx/锁即可构造此窗口，本次没有运行该反例，也不声称模拟了网络 ACK 故障。

这违反已接受卡 §5.3 的 committed 重放独立于 live 配置、以及 §8“取得同一原 writer 屏障后按 canonical preparation/binding/snapshot/lease 重验”的规则。当前权限检查本身存在；缺的是屏障后的本域状态确认。

最小修正：preflight 在完整当前锁与 consumer 验证后重读 preparation，比较候选的存在/ID/版本/phase/实际内容。发现变化先 RESOURCE_BUSY，结束 Tx 后整轮重新规划；不在持锁 Tx 内 Discover、补锁、换 SnapshotID/LeaseID，也不能把缓存 readErr 当作确认后的不存在。原存在性错误仅可在原候选仍成立时交付。针对性回归应保留修前输入，明确实际 first read、旧 writer commit、live 配置变更、同一 Command 屏障及精确错误/重入结果。
