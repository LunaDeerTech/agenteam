## 已确认决定

### P01-01：对象 ID

- 用户选择：A，统一 UUIDv7。
- 适用：User、Project、Task、Agent、Execution 等持久化对象。
- API：ID 以字符串传输；ID 不代表访问权限。
- 取舍：可分散生成，按生成时间大致有序，有利于索引局部性；包含大致创建时间。
- 后续：D01 固定公共类型与跨模块约定；各模块规格落实字段、约束和引用，不在此创建业务实现。

### P01-02：时间

- 用户选择：A，UTC + RFC 3339 字符串。
- 时间点字段使用 PostgreSQL timestamptz，统一微秒精度；API 返回 UTC RFC 3339 字符串；前端按用户本地时区显示。
- 排序与并发判断由服务端完成，不依赖浏览器保留微秒。持续时长与纯日期字段另行定义。

### P01-03：HTTP 错误格式

- 用户选择：A，RFC 9457 Problem Details。
- 扩展字段提供稳定业务错误码、request_id 和字段错误；不暴露内部堆栈或敏感信息。
- D01 规格仍须确定具体字段、状态码映射及可执行示例；本次选择只关闭格式方向。

### P01-04：列表分页

- 用户选择：A，游标分页。
- 使用稳定排序位置获取下一页；适合持续变化的列表，不支持直接跳到任意页。游标本身不保证完整快照一致性。
- D01 规格须落实排序及唯一决胜字段、游标编码/校验、筛选绑定、分页大小和失效规则；领域特定分页由相应规格明确。

### P01-05：更新版本与冲突处理

- 用户选择：A，统一请求字段 expected_version。
- 可编辑对象读取返回 version，修改提交 expected_version；不匹配则拒绝修改，调用方重新读取后决定。前端、Agent Tool 和内部服务统一表达。
- 不新增 HTTP ETag/If-Match 版本转换要求。字段类型、适用命令、冲突状态码及事务内推进规则由 D01/领域规格落实；保留已有 Task 幂等解析先于版本校验规则。

### P01-06：请求追踪与幂等标识

- 用户选择：A，HTTP request_id 与业务 idempotency_key 分开。
- 每次 HTTP 请求具有独立追踪 ID；同一业务操作重试沿用幂等键。同键同参数返回原结果，同键不同参数拒绝执行。
- 现有领域契约里用于幂等的 request_id 须在 D01 明确映射，不能直接解释为每次 HTTP 请求的追踪 ID；已有 Task 幂等解析先于版本校验规则保留。
- 幂等作用域、参数规范化、结果存储和保留期限、并发及 unknown outcome 处理仍须在具体契约中确定。

### P01-07：跨模块契约组织

- 用户选择：A，按职责建立独立契约包，由调用方与实现方共同依赖；契约包不包含业务实现。
- 用户补充约束：避免循环引用；包和目录结构必须合理，不能无脑集中堆放。
- 组织原则：按稳定业务职责和依赖关系拆分，不建立万能 contracts/shared 包承载全部领域；按实际需求增加，避免大量空包和无必要的细碎包。具体目录树在 D01 规格中审查。
- 所有方案继续遵守正式端口与事实归属：模块不能绕过对方服务直接改表；Runner 不依赖 Central 业务包，共享通信契约保留在 internal/runnerprotocol。

### P01-08：跨模块事务协调

- 用户选择：A，通过统一事务接口协调，确需参与同一数据库事务的正式端口显式接收事务上下文。
- 各模块只操作自己拥有的数据；业务契约不直接依赖具体数据库驱动。仅在需要原子性的边界共享事务，不建立覆盖整个工作流的长事务。
- 外部请求、邮件与对象存储副作用不属于数据库原子事务，需按对应模块的 outbox、补偿或 reconciliation 契约处理。
- 具体接口、锁顺序、事务拥有者及异常传播由 D01/D03/领域规格落实。

### P01-09：取消请求的返回语义

- 用户选择：A，取消请求持久化后立即返回已接受，后台继续停止；调用方通过查询或实时更新确认最终状态。
- 仅实际停止后标记 cancelled；重复取消安全；已有副作用不自动回滚。调用请求断开或超时不代表执行已停止。
- D01/执行相关规格须落实状态返回、HTTP 状态码、权限、终态取消结果、控制传播及 unknown outcome 处理；不得以请求已接受替代停止证据。

### P01-10：领域事件数据

- 用户选择：A，payload 携带表达事件所需的最小数据：对象 ID、版本、事件类型及必要变更信息；其他展示数据通过事实所属模块查询接口获取。
- 不允许仅凭 ID 猜测历史变更；不复制完整业务对象作为默认策略。领域事件由事实所属模块定义和发布，随业务变更在同一数据库事务写 Outbox。
- 事件排除凭据及 Secret；具体 schema version、去重、乱序和消费者处理规则由 D01/D06/各领域规格落实。

### P01-11：HTTP DTO 与内部领域类型

- 用户选择：A，分开定义并显式转换。
- HTTP DTO 只包含允许接收/返回的字段；内部领域类型按业务职责设计。转换放在对应模块 HTTP 适配层，按职责组织，不集中堆放全部 DTO。
- D01 及模块规格落实字段映射、输入验证、授权后的输出投影和 API 版本兼容；不通过直接序列化内部对象暴露敏感字段。

### P01-12：删除与引用保护

- 用户选择：A，各模块通过正式生命周期端口参与；对象所属模块发起删除，相关模块提供引用检查、替换或清理能力。
- 必要能力未绑定或检查失败时明确拒绝或保留待处理状态，不宣称删除成功。跨模块禁止直接改表，不以统一数据库级联替代领域规则。
- 软删除、永久清理、历史引用及适用的事务/补偿规则按领域确定。D01 固定矩阵和端口，后续模块落实真实适配与验证。

### P02-01：基础依赖版本选型原则

- 用户选择：B，优先复用当前环境版本作为候选，核验兼容性和可用性；不满足项目要求时更换。
- 当前候选：Go 1.27.1、PostgreSQL binary 17.8、pgvector 镜像标签 0.8.1、MinIO RELEASE.2025-09-07T16-13-09Z。
- 此决定是候选优先级，不能据此宣称版本已验收或已加载 pgvector；正式固定版本/镜像摘要、集成测试条件及风险说明由 D02/D03/D05 规格落实。

### P02-02：HTTP 服务与路由

- 用户选择：A，使用 Go 标准库 net/http + ServeMux，不引入 chi 路由依赖。
- handler 按模块组织，业务逻辑不放在路由层；公共登录、日志等步骤通过中间件组合。WebSocket 等能力另选专用库。
- 用户询问差异后已说明现代标准库支持方法和路径参数、chi 主要提供路由分组与中间件组合便利，选择不决定业务模块边界。

### P02-03：PostgreSQL 访问方式

- 用户选择：A，pgx 驱动 + 显式 SQL，不采用 GORM 等 ORM 作为数据库访问框架。
- 明确控制事务、行锁、唯一约束与向量查询；数据库结构由全局正式迁移维护，不自动修改生产表结构。
- pgx 具体版本、连接池、统一事务接口的适配、查询组织与检查命令在 D03 规格核验后固定。此选择不自动授权额外 SQL 代码生成依赖。

### P02-04：数据库迁移工具

- 用户选择：A，Goose，维护全局 SQL 迁移序列，可嵌入 Central 启动流程；不按领域各建独立迁移器。
- 常规迁移使用事务，确实不支持事务的 SQL 必须显式标记；迁移锁、失败状态和恢复须通过真实 PostgreSQL 验证。
- Goose 固定版本、pgx 配套连接方式、迁移文件规范、锁及恢复流程在 D03 规格落实；不因库默认行为宣称所有迁移可自动安全回滚。

### P02-05：加密能力的库选型方式

- 用户选择：A，Go 标准加密库优先，缺少的能力按需采用 golang.org/x/crypto 等成熟专用库，不引入 Tink 作为统一框架。
- 不自行发明加密算法；具体算法、数据格式、密钥版本与轮换流程由 P03/D04 确定，密码哈希由 P04/D07 确定。
- 专用库按确需能力核验并锁定版本，不因方向选择自动增加所有依赖。

### P02-06：基础设施集成测试环境

- 用户选择：A，独立测试容器，使用与项目固定版本一致的 PostgreSQL/pgvector/MinIO；测试数据可创建清理，重启与故障恢复在隔离环境进行。
- 不使用业务数据；生命周期、资源清理、版本固定和可执行测试命令由 D03/D05 等规格落实。

### P03-01：Secret 加密算法

- 用户选择：A，AES-256-GCM，遵循既有信封加密边界：数据密钥加密 Secret，部署主密钥保护数据密钥，主密钥不存业务数据库。
- 使用 Go 标准库能力，正确生成密钥并确保同一密钥下 nonce 不重复；密码哈希另在 P04 决定。
- 数据格式、认证附加数据、密钥版本、nonce/密钥生命周期及轮换恢复由 D04 规格落实，不能仅凭算法选择视为安全实现已验收。

### P03-02：部署主密钥轮换

- 用户选择：A，带版本的多主密钥，后台分批重新保护数据密钥，迁移可中断恢复；新写入使用新主密钥，存量数据迁移和迁移中断恢复要求满足后才移除旧密钥。
- 用户补充：最终通过 Docker 部署，主密钥及此类技术部署配置希望从环境变量读取；询问分批自动迁移是否需要数据库持久化。此要求不把既定 Runtime Platform Config 全部改为环境变量。
- 已说明的边界：原始主密钥/密钥环只由部署环境注入，不保存到业务数据库。数据库可持久化被加密保护的数据密钥、非敏感 key version/算法格式、迁移状态/进度和错误等元数据，用于中断恢复。不能将迁移需要持久化解释为允许明文主密钥入库。
- 后续规格建议（非已实现能力）：部署通过环境变量给出有效密钥版本及当前写入版本；Docker 环境变量变化需要更新部署并重启 Central，重启后读取新配置并恢复迁移。自动分批迁移不等于自动生成、轮换或回写部署主密钥。具体编码、配置校验、并发和 checkpoint/恢复规则由 D04/D28 规格落实。
- 旧密钥退役须确认存量记录迁移完成；无凭据写入记录或日志。

### P03-03：内网访问白名单

- 用户调整：白名单不应仅作为基础设施环境配置，服务器启动后应由管理员在系统配置 UI 中维护，提高灵活性。
- 用户最终选择：A，网段 + 可选端口限制；每条规则指定网段，可填写允许端口或显式选择全部端口。
- 确认方向：管理员系统运行时配置，保存数据库；不将主密钥转入数据库。此前 P03-02 的技术部署配置环境变量要求对此白名单作明确例外。
- 设计影响：原 outbound-network-policy §7 与部署架构将白名单设为部署级、运行配置不能扩大部署边界，需在决定完成后同步修订；D04 负责政策持久化及正式端口，D07/D08 提供身份/系统授权，D26/D27 提供管理员 UI，D09/D20/SMTP 调用接入策略。
- 既有固定禁止地址与 Project/Agent 不可修改系统策略规则保留；默认不放行内网。保存验证、Audit、策略版本、更新生效和已有连接行为须在规格明确。

### P03-04：白名单更新对在途请求的影响

- 用户选择：A，新请求立即使用新规则，已发出的在途请求继续执行，不主动中断。后续重试及重定向也重新检查当前策略。
- 策略以数据库为权威，无需重启 Central；连接复用不能成为新请求绕过最新策略的途径。
- 已发出请求的边界、策略 version/cache 更新、DNS/dial/redirect 检查及并发语义在 D04 规格明确；不承诺修改配置能撤回已发生的外部副作用。

### P03-05：内网明文 HTTP 的放行方式

- 用户选择：A，白名单规则放行网段/端口后默认仍要求 HTTPS，需要的内网规则由管理员显式开启允许 HTTP。
- 地址可达与明文传输授权分别控制；HTTPS 正常校验服务端证书，不通过关闭证书校验支持自签名证书，私有证书通过受信任证书配置支持。
- 当前决定仅针对内网 HTTP 类调用；SMTP 的 none/STARTTLS/TLS 协议适配与策略另在对应规格明确，不把 SMTP 当作 HTTP 客户端调用。

### P03-06：Audit 记录范围

- 用户最初暂选 B，并担心 A 不保存正式工具记录；澄清后用户最终选择 A。
- 必须澄清：A/B 均保留正式工具调用记录（ToolOperation/Attempt、Canonical Transcript 及对应运行证据）；选项仅决定低风险调用是否额外追加 Audit 摘要，不决定是否保存工具调用。B 不能替代正式工具记录，也不授权 Audit 复制完整参数/结果/输出。
- 最终规则：Audit 聚焦关键配置修改、审批、Secret 使用、Runner 身份变更、授权拒绝、高风险/结果未知的敏感操作；普通低风险工具调用不额外复制 Audit 摘要。所有工具调用仍保留正式调用记录及对应 Transcript。

### P04-01：密码哈希算法

- 用户选择：A，Argon2id，密码只保存不可逆验证结果，不用可解密 Secret 加密代替密码哈希。
- 使用随机盐并保存算法/参数，以支持后续升级；参数结合服务器性能测试确定，并限制哈希验证并发，避免内存耗尽。
- D07 规格须明确编码格式、参数/升级、资源限制、登录失败路径和可执行验证；未采用 bcrypt，未固定尚未经测量的参数。

### P04-02：密码设置规则

- 用户选择：A，15–128 个字符，允许空格/中文，不强制大小写/数字/符号组合，拒绝常见弱密码。
- 不静默截断，不去掉首尾空格，不要求无故定期改密。
- D07 规格明确字符计数/编码、弱密码列表来源、请求大小限制与所有设密入口一致性；未授权引入外部密码泄漏查询服务。既有首次管理员密码提示不改为强制改密。

### P04-03：登录会话有效期

- 用户原选择：A，连续 7 天不活动过期，绝对有效期自登录起最长 30 天；后续 P04-05 用户要求改为管理员系统 UI 可配置，这些数值成为默认值而非固定业务常量。活动可延长空闲有效期，不突破绝对期限。
- 服务端管理会话；退出立即使当前会话失效。网页登录过期不自动取消已运行的 Agent Execution。
- D07/D25 规格落实可信活动定义、刷新节流、API/WS 过期重校验、cookie 属性与撤销并发；不因浏览器仍连接而无条件延长会话。

### P04-04：改密与重置后的会话撤销

- 用户选择：A，普通改密验证旧密码后给当前设备换发新会话，撤销其他旧会话；忘记密码重置撤销全部会话并返回登录页。
- 同步使相关旧 WebSocket 身份失效；不自动取消运行中的 Agent Execution。
- D07/D25 明确密码与会话变更事务、令牌轮换、响应丢失、旧连接终止和 API/WS 撤销竞争行为。

### P04-05：会话与密码重置期限可配置

- 用户新增授权需求：提供创建技能的技能或工具；支持下载并导入第三方技能到项目库；还需 Agent 可调用的下载/导入工具，将第三方平台的技能导入当前所在项目。
- 主线程建议统一项目 Skill Domain：管理 UI 和 Agent 工具共享创建/校验/发布/import 服务，使用 ObjectStorageService 持久化不可变包版本，不能另设 Runner 本地技能库作为事实来源。
- 工具候选包括创建技能、从 URL/受支持来源下载导入，以及查找/读取项目技能；具体名称/schema/风险/幂等与来源适配范围待规格或后续问题确认。用户所称“创建技能的技能”可作为使用创建工具的指导内容，但不以提示词代替正式持久化能力。
- 此前主线程建议第三方下载由 Central 的正式出站客户端执行；P07-11 用户进一步确定由引导技能组织查找/获取/编写，最后通过统一安装工具提交标准包，下载不再预定为专门技能导入 Tool 的内置动作。实际搜索/下载能力须正式授权及验收；导入不自动执行脚本/安装依赖，运行文件仍遵循 P07-08 Runner 直连对象存储。
- Agent 创建/导入只能写当前 Project，工具受 Agent Capability、Execution Policy、Project 归档/删除门禁和统一授权/审批约束，不擅自增加为不可关闭 Core Tool。重名与失败不静默覆盖既有技能，具体冲突规则待确认。
- 项目库共享可见性、导入后如何供当前/其他 Agent 使用及当前 Execution 的版本固定，尚需 P07-10 决定；第三方具体平台/格式范围亦待确认，不宣称可导入所有平台。
- 影响 D01/D04/D05/D10/D18/D21/D22/D27/D28：新增管理/导入端口与包发布状态、正式工具、出站/对象/Runner 绑定及 UI；具体设计草案已同步，未实现产品。

### P07-10：按 Agent 分配技能与操作维度

- 用户明确不希望项目中所有 Agent 都能看到全部技能，要求按需使用。最终方向采用逐 Agent 分配/白名单，而不是 P07-10 候选 A 的项目全库共享；允许读取的技能仍按需加载完整说明。
- Owner 的项目技能管理目录与 Agent 的可见技能目录分别授权，Agent 不因所属 Project 就获得全库发现/读取；按当前 Agent 的正式技能引用过滤名称/简介及包文件，不能只隐藏前端。
- 用户澄清操作维度：Agent 是创建技能、下载技能（即第三方导入）；用户侧只有导入技能，通过前端按钮/界面执行，不新增人工创建/编写技能的独立流程。
- 用户询问 Agent 创建/下载应是 Tool，还是项目固有/系统内置不可删除的 Skill。主线程建议正式 Tool：Skill 是说明与方法，Tool 是可验证、可授权、可记录的下载/创建/入库执行能力；即使配引导 Skill，底层仍需正式能力。
- P07-11 用户已进一步指定不可删除的引导 Skill + 一个统一安装 Tool，替代先前两个专门创建/下载工具的候选；工具是否 Core、自动授权创建者及当前 Execution 动态使用仍待确认。
- 新创建/导入的技能如何分配给发起 Agent、何时对当前 Execution 可用及版本引用保护，后续单独固定。读取项目全库的草案建议已撤销，技能作用域仍仅 Project。

### P07-11：不可删除的引导技能与统一安装工具

- 用户指定的新方案：先提供不可删除的内置 Skill（候选名 Create Skills / Add Skills，草案暂称 Add Skills），让 Agent 按两条路径获取技能：先查找市场/网络是否已有可用技能；没有合适内容时再自行编写或将经验总结成技能。
- 两条路径最终均产出标准技能包，包括 SKILL.md 与必要文件；通过一个正式安装/上传/转换 Tool 将包发布到当前项目技能库。暂称 install-skill，确切名称/schema 在规格冻结，不保留两个独立 create-skill/import-skill 专门工具的先前提案。
- 用户前端的技能包上传/导入入口，与 Agent 安装 Tool 调用同一 Skill Domain 安装服务，共用包校验、对象存储、metadata/版本发布、幂等/冲突与失败清理，不维护不同格式或两条发布旁路。
- 引导技能只提供查找/选择/编写/打包/安装的流程说明，使用已获授权的搜索、下载、文件、命令及 Artifact 等能力；不存在或未绑定的搜索/下载工具须明确补齐正式契约与验收，不能仅靠指令宣称已经具备。安装包不会自动执行脚本/安装依赖。
- 维持项目级技能管理：引导技能作为项目内置受保护资源，不能单独删除，但不建立系统共享技能目录；项目永久删除可以清理它和项目其他资源。默认向哪些 Agent 分配与管理升级细节待确认。
- 安装工具输入是标准包/受控文件引用；来自 Runner 的包按已确认直传对象路径获取并校验，来自平台文件的引用经 Project 业务授权，用户上传也形成受控包材料。具体 Artifact/Runner/上传引用 union 与完整性在 D01/D05/D10/D17/D21 落实，不让模型提供 MinIO key 或凭据。
- 此决定替代 P07-09/P07-10 讨论中的专门创建/下载工具建议；保留第三方获取需求、逐 Agent 技能可见、按需加载、版本固定及不自动扩大工具权限。新包安装后如何分配/在当前 Execution 使用仍待决定。
- 影响 D01/D08/D10 的内置技能初始化/正式安装端口，D05 存储、D18/D21 Tool 适配、D22 运行版本与引导加载、D27 用户导入、D28 全流程。不能用生产占位成功替代尚未绑定的初始化或传输能力。

### P07-12：Add Skills 的最初固定可见要求（已由 P07-13 调整）

- 用户当时要求内置引导技能与不可禁用 Core Tools 一样固定可见；后续 P07-13 用户重新考虑并明确撤销不可禁用要求，改为默认启用且可按 Agent 禁用。本节只记录历史，最终规则以 P07-13 为准。
- 最终仍不开放项目其他技能全库；Add Skills 是项目内置资源，不能单独删除，但可从某个 Agent 的可用技能中禁用/移除，项目永久删除按项目资源清理。
- 与 P07-07 按需加载一致：固定可见/不可禁用指技能可用性，完整说明仍通过正式读取能力按需加载；不解释为每次任务必须执行技能获取流程或预加载全部正文。
- D01/D08/D10/D18/D21/D22/D27 根据 P07-13 最终规则落实受保护身份、初始化与版本、默认分配和按 Agent 禁用，不实施此前候选的只读配置或永久可见例外。
- 技能指导不授予额外工具权限、不跳过 Execution Policy/服务端授权或审批。安装工具最终按 P07-13 为默认启用的普通可配置工具，不加入不可禁用 Core Tools。

### P07-13：引导技能与安装工具默认启用、允许禁用

- 用户重新考虑并指定最终规则：Add Skills 默认对 Agent 可见/启用，但用户可以让某个 Agent 不使用它；配套 install-skill 同样默认启用，也可以禁用，因为不是所有 Agent 都需要创建技能。
- 本决定覆盖 P07-12 的固定可见/不可取消要求，不新增不可禁用的技能能力或 Core Tool。
- 项目内置 Add Skills 资源不可单独删除的 P07-11 规则保留；资源保留与 Agent 使用开关分开。Agent 禁用后不获得该技能的目录/说明或安装工具能力，普通技能仍逐 Agent 授权。
- D10/D18/D21/D22/D27 落实创建时默认配置、用户显式禁用及执行上下文的有效集合；保存/重新加载/模板复制/重启不得覆盖用户的禁用配置。引导技能与安装工具分别按技能引用/allowed tools 管理，不让读取指导自动重新开启已禁用的工具。
- 已运行 Execution 的配置快照与实际调用授权继续按正式模块规则落实，不以此决定承诺回滚已经开始的操作；默认启用不跳过审批、Execution Policy、Mount 或项目生命周期约束。
- 新安装技能是否自动加入发起 Agent，以及当前执行如何按固定版本使用，待 P07-14 等后续问题确定。

### P07-14：Agent 技能分配工具

- 用户要求新增普通可选的系统内置工具，给某个 Agent 分配某个技能，相当于用户在后台勾选技能；允许秘书类 Agent 统一为其他 Agent 配置技能，支持 Agent 自我管理。
- 主线程建议命名 `assign-skill`（分配技能），区别于 `install-skill`（把标准包安装到项目库）。名称在正式 schema 冻结，不以用户口语“安装”混淆包发布与 Agent 配置。
- 工具属于普通 Builtin Tool，由 Agent 配置选择是否授予，不是不可禁用的 Core Tool。用户只明确可选，未要求所有 Agent 默认开启该管理工具。
- UI 勾选与 Tool 调用同一 Agent Skill assignment 服务，处理 Agent 版本、规范化稳定引用、幂等、并发冲突、已删除/禁用技能及项目归档/删除门禁，不直接修改数据库关系旁路。
- 目标 Agent 与技能必须属于当前 Project，不能跨 Project 分配；有该工具能力的 Agent 可管理同项目其他 Agent 的技能配置，但不由此获得修改模型、Secret、Mount、工具授权或审批策略的能力。
- P07-10 的普通技能逐 Agent 读取范围保留；管理技能清单/分配与读取正文是不同权限。P07-15 已选择 A：拥有有效 assign-skill 权限的 Agent 可查询并分配整个当前项目技能库中的合法技能。
- 本次提出新的分配工具，没有明确回答原 P07-14 安装是否自动分配给发起 Agent；该默认仍待决定。工具还需明确添加/移除操作范围、是否作用于运行中的 Execution 与使用版本固定，不擅自覆盖既有快照。
- 影响 D01/D10 技能分配端口/配置事务，D18/D19/D21 Tool schema/ScopeResolver/授权/审批及调用，D22 新旧 Execution 一致性，D27 UI 同服务绑定。当前仍为设计记录，未实现工具。

### P07-15：分配工具的技能管理范围

- 用户选择：A，拥有 assign-skill 管理权限的 Agent 可以查询当前 Project 技能库的名称/简介，并向同项目 Agent 分配任意合法技能，不要求调用者自身已被分配该技能。
- 完整技能正文/脚本/素材的读取仍按调用 Agent 自身技能配置及正式权限校验；管理目录可见不自动赋予内容读取权限。未获得管理能力的 Agent 继续只看自身已分配技能。
- 查询与分配均限制当前 Project，管理查询端口应校验当前有效工具/执行权限，不能仅凭客户端参数或某条静态配置打开全库目录。
- D01/D10/D18/D19/D21 明确管理目录查询、目标 Agent/Skill 校验、分配命令及 ScopeResolver；既有版本/幂等/项目生命周期门禁仍适用。
- 安装是否自动分配给发起 Agent 尚未决定，下一问题 P07-16 补齐；不将管理范围选择推导为安装自动授权。

### P07-16：安装技能后是否自动分配给发起 Agent

- 用户选择：A，install-skill 只将标准包安装/发布到项目技能库，不自动分配给发起安装的 Agent。
- Agent 可接着通过已获授权的 assign-skill 分配给自己或同项目其他 Agent；用户前端上传也只安装到库，通过后台技能配置明确分配。
- 安装与分配保持两个独立业务动作、各自版本/幂等与结果。安装成功而后续分配失败时，已发布的项目技能保留，不能把分配失败误报为安装未发生或自动回滚整个包。
- Add Skills 引导文案须说明安装后按需求显式分配；未获 assign-skill 管理权限的 Agent 不能因自行安装就获得分配能力，仍可由用户或获授权的其他 Agent 完成分配。
- P07-17 继续明确新分配技能对当前运行中 Execution 的生效时点与版本固定，不将分配成功直接推导为当前上下文已经更新。

### P07-17：下一轮使用新技能与 Execution 架构核对

- 用户明确理想目标为 A，新分配技能在当前执行下一轮即可使用，并要求核对已有 Agent Execution 架构是否冲突。按此记录业务目标；详细接口与架构同步仍待落实。
- 核对发现真实契约调整点：Execution Context §2/§10 规定启动 Context immutable 且 Agent 配置变化不影响当前 Execution；Execution Domain Model §4 固定启动 Agent capability/Tool Snapshot；Tool Registry §6 固定 ToolSpec/schema/binding。直接改快照或每轮重读全部配置不符合现有规则。
- 现有扩展基础：Loop Runtime §4–5/§18 已在稳定轮次边界消费正式 typed control input；Transcript §9/§18/§40–41 支持记录运行时控制事实、每轮 projection 与 checkpoint 恢复。但当前类型未包含技能变更，不能声称已经支持动态技能。
- 已补充技能草案 §3a：保留初始 Snapshot，由正式分配事务/执行端口可靠提交新增技能绑定，包含固定 revision；Executor 在下一轮输入确定点应用，生成可追溯控制记录。初始技能 + 已生效变更共同构成本次运行目录，恢复/压缩后仍可重建。
- “下一轮”指下一次 Model Request 输入确定点之前已提交的分配；当前已发出的请求和 Tool Batch 不被改写，waiting 不因技能变更解除，终态不复活。详细锁序/去重/启动竞争/事务投递在 D01/D10/D22 确定，不能仅靠可能延迟的通知承诺下一轮。
- 仅新增技能资源绑定，不自动增加 Tool、改 schema、换模型或授予新的 Runner/Secret 权限；当前 Execution 必须已有所需通用技能工具和执行工具。读取说明/素材/Runner 落地使用一致的绑定版本。
- 需要同步 Agent Management、Execution Context/Domain/Lifecycle、Loop Runtime、Transcript/Checkpoint 与技能工具专题；此处为可审阅的架构调整草案，原架构正文与产品实现均未修改。撤销/升级等具体行为后续明确，不扩大成所有配置热更新。
- 证据：execution-context.md §10/§15，execution-domain-model.md §4，tool-definition-registry.md §6，loop-runtime.md §4–5/§18–19，transcript-context.md §9/§18/§40–41，execution-lifecycle.md §15。

### P07-18：同名技能包的安装与升级策略

- 用户选择：A，安装同名技能包默认提示冲突，只有明确选择更新后才发布新版本，不自动将同名安装视为覆盖/升级。
- 更新创建不可变新 revision，已运行 Execution 继续使用此前固定的旧版本，不因发布更新而静默替换。
- UI 上传与 install-skill 使用相同冲突/显式更新语义。Tool 输入须明确更新目标与预期版本，不能仅凭包内名称或来源名称覆盖另一个技能；具体字段、名称规范化及并发校验在 D10/D21 规格固定。
- 重试沿用 P01 幂等规则，不能因响应丢失重复发布版本；更新失败保留原版本，发布/对象写入失败的清理与可恢复性按统一安装服务落实。
- 内置 Add Skills 的受保护身份及版本维护另按其正式规则处理，普通同名包安装不绕过保护。

### P07-19：移除技能时不额外干预运行中的执行

- 用户不选择主动处理运行中执行的方案，要求直接不管已运行 Execution；后续使用遇到问题时返回错误，由 Agent 自行应对。
- 移除/禁用只更新正式配置，不因此停止 Execution/已开始的脚本、不改写历史快照或 Transcript、不增加专用撤回通知和强制上下文清理流程。已有模型内容与工作区文件不自动收回。
- 后续技能读取/准备调用继续执行原有当前资源与授权检查；资源不存在或权限不再满足时返回正常 ToolError 给 Agent，不伪造成功，也不承诺旧权限一直可用到执行结束。普通可恢复工具错误不自动终止整个 Execution。
- 已确认的新增技能下一轮生效（P07-17）保留；新增绑定应用前必须验证分配仍然有效，不能由延迟的新增通知恢复已移除授权。此校验由 Executor/Skill 正式端口负责，不引入每轮重新读取全部 Agent 配置。
- 这是用户指定的自定义规则，不记为此前 B“当前执行保留全部旧访问权”。D10/D21/D22 落实正常错误及并发分配/移除，避免为移除增加超出需求的执行编排。

### P07 规格落实边界

- 模板、Agent 标识/显示名、项目技能及运行中变更的业务方向已记录；[技能草案](d00-skills-design-proposal.md)保存新增能力和跨模块影响，尚未同步所有架构原文或冻结正式接口。
- D01/D10 补齐 Agent/Skill canonical 字段、版本/引用/删除保留矩阵与正式目录/白名单端口；D15/D18/D20 分别提供真实 Runner/Mount、Tool Registry、Project MCP Connection 查询绑定，目录缺失或失败不得当作验证通过。
- 模板不包含项目 Mount/Secret/Approval/Memory，工具推荐只使用平台内置工具；实际 Agent 的模型、Mount/Workspace、Tool、Skill 和 Secret 引用逐项按正式作用域校验。Runner 暂时离线属于实际调用错误，不等同于长期引用消失。
- Secret 白名单使用项目变量稳定引用，执行上下文只包含获授权 Secret 的名称/说明，值由正式 Secret/执行注入能力解析；不由技能或任意工具配置扩大白名单。
- Skill 具体包格式/校验参数、版本/删除与对象清理、读取/准备/安装/分配 schema、内置引导维护、目录元数据及搜索/文件获取的真实能力尚须 D01/D05/D10/D17/D18/D21/D22 规格及验收落实；不因讨论结束声称模块已完成或生产端口已绑定。

### P19-01：Launch 结果未知时沿现有流程继续自动核对

- verification_worker（gpt-6-astra / max）与主线程独立核对 [Dispatch §12–15/20–21](../../architecture/scheduler/scheduler-dispatch.md)、[Loop §12](../../architecture/scheduler/scheduler-loop.md)和 Executor Launch。§13 要求 unknown 保持原 Dispatch/key 直到结果确定；§15 却把 unknown retry 耗尽也归 failed + Task blocked，failed 又不走 pending 恢复。本次决定用于消除该不一致。
- 场景：启动请求已经发出，Executor 可能已创建 Execution，但回复丢失。有限 Launch retry 耗尽后，仍不能证明“没启动”。直接换新 key 再发起可能重复执行；重复调用 Launch 本身也不是纯查询，因为原 key 没有记录时仍可能创建 Execution。
- **用户选择 A，并明确简化：** 一直无法确认就继续自动核对，沿用现有 Scheduler 串行 traversal/recovery/pacing 和 Executor 的持久化事实；保留原 Dispatch/key 与防重复派发，展示真实待确认状态，不为核对另建服务、独立 timer worker、多阶段校验或通用救援系统。
- **B（未采用）：** 不新增“重试耗尽后必须由 Owner 点击核对/恢复”流程。未知结果不因有限启动 retry 用尽而直接改成 failed + Task blocked，也不改成无限重复发起启动；普通已知暂时错误的有限 retry 规则不因此全部取消。

### C02 只读核对与同步缺口

- [Runtime View §4/19–21](../../architecture/agent-executor/runtime-view.md#20-snapshot-与-stream-race)用 seq 表示条目创建顺序，又在快照衔接时丢弃 seq 不大于 max_seq 的更新；item_revision 仍是可选字段。已存在条目的后续 delta/updated/completed 不会因此获得新的创建序号，两种含义不能混用。
- 例：快照包含 seq=7 的运行中工具，列表最大创建序号为 12；随后同一工具 completed 更新仍为 seq=7，旧比较规则可能把它丢弃。verification_worker（gpt-6-astra / max）与主线程确认这是未关闭的契约缺口，尚无产品实现可宣称已复现故障。
- 保留低延迟流式 delta、先订阅再取快照、批量/节流保存当前快照、断线重读等既定规则。新的更新边界必须对应返回快照实际包含的内容，不能直接取“最新已发送编号”而遗漏尚未 flush 的变化；不逐 token 写库，不新增持久 delta 日志或平台全局可靠回放。
- 两种方向均须处理重复、乱序、文本增量缺口和终态更新；无法接续时按现有 Snapshot/resync 契约重新读取。[Meeting 展开执行视图](../../architecture/meeting/meeting-timeline-realtime.md#23-reconnect)复用同一 Runtime 契约，Timeline/Inbox 自身的 invalidation 规则不因此改为全局更新序列。

### C02-01：Runtime 快照与实时更新如何衔接

- 用户选择：**A，每次 Execution 独立维护统一更新进度。** 条目创建 seq 只负责排序，可见的 started/delta/updated/completed/failed 等变化推进独立更新编号；更新范围是单次 Execution，不新增平台全局更新序列。
- 快照返回实际已包含内容的更新边界，客户端从该边界衔接后续变化；不能用条目最大 seq 或“最新已发送编号”代替快照水位。须覆盖节流 flush 间隙，以及同一已存在条目的后续内容/终态变化。
- 重复、乱序、增量缺口及重启按正式 Snapshot/resync 契约处理，旧更新不能覆盖新状态。需要的条目 revision/文本 offset、分页/筛选下的边界、计数延续或重启代际等由 D01/D22/D25 工程规格固定；不逐 token 写库、不增加持久 delta 日志，不以仅重读替代已定流式体验。
- 不采用 B 的“无 Execution 级统一进度、仅逐条目对齐”方向；这不禁止 A 内部使用必要的条目版本/文本基线来安全应用增量。
- 不改变工具/任务业务状态机。D01 固定端口，D22 产生更新，D25 实现投影/恢复及 race 验收，D24/D26/D27 同步引用与客户端；字段编码、数据结构与算法不另作产品微选项。
- 用户决定已记录；未修改 Runtime/Realtime/Meeting 架构原文或产品代码，正式契约和真实验收仍待落实。

### C02 收尾核对

- D01/D22/D25 必须覆盖“订阅前已发送、但尚未写入所读快照”的变化；仅把条目序号换成更新序号，或仅返回持久化水位，均不能自动补回这段内容。快照读取/flush/恢复契约须保证完整衔接，具体机制及乱序/缺口/重启场景由工程规格与真实测试落实，不增加持久 delta 日志。

### C03 只读核对与身份边界

### C04 只读核对与重试边界

- [Loop 总览 §8](../../architecture/agent-loop/README.md#8-model-system-边界)与 [Loop Runtime §20](../../architecture/agent-loop/loop-runtime.md#20-model-request-error)把 Provider 请求重试交给 Model System；[Chat Runtime Error Normalization](../../architecture/platform-infrastructure/model-system/chat-model-runtime.md#error-normalization)则写由 Loop 根据 retryable 和策略决定重试，[Usage §6](../../architecture/platform-infrastructure/model-token-usage.md#6-invocation-identity-与-retry)也画出 Loop 重试同一 logical turn。责任冲突不能全部解释成新的语义轮次，须统一。
- 本题只选择 Agent 执行中同一次逻辑模型调用的自动请求重试 owner；不把上下文压缩后重新调用、模型看到工具错误后的修正、用户 retry/regenerate 或 Scheduler relaunch 合并为同一种技术重试。Tool Runtime 继续拥有工具重试与副作用安全。
- 保留单次 Model Request 的渐进 timeout、backoff、取消优先及既定错误分类；达到最大单次 timeout 后可按策略继续，Model timeout 本身不作为 Execution 终止条件。单轮 watchdog 中止当前 generation 后继续执行，不新增 Execution 总期限，也不借选择 owner 统一改成固定重试次数。
- 每次真实 Provider 请求独立生成 Invocation/Usage 事实，失败尝试已报告的 Token 仍计入；不能由两层或 SDK 的隐藏重试增加未记录尝试。流已输出部分内容时，需区分各 attempt 的输出/稳定 Transcript，不能把不同尝试盲目串接为一次完整回答，不执行半截 Tool Call，不因模型重试重做已执行工具副作用。
- [自动审批不自动 Retry](../../architecture/security-governance/auto-approval-model/approval-model-contract.md#不自动-retry)禁止审批模块再加应用层重试，但允许已有平台 Adapter 透明网络重试；审批模型有限请求 timeout/失败转人工及人工持久等待不变。其他 consumer 的既定规则不因本题变成统一无上限或统一有限次数。
- D01/D09/D22 统一重试责任、规范化错误、attempt 关联、流式输出边界与 cancellation；具体策略参数、SDK 配置和真实故障/计量验证留工程规格，不把业务失败恢复移入 Model Adapter。

### C04-01：Agent 模型请求的自动重试由谁管理

- 用户选择：**A，Model System 统一管理。** 同一次 Agent 逻辑模型调用中的 Provider 自动请求重试由模型服务负责，Agent Loop 接收标准化流/结果及最终错误，不再额外重试同一请求；不采用 B 的 Loop 重试 owner。
- 同一路径只有一个自动重试责任层；SDK/Adapter 的实际尝试须纳入统一策略和 Invocation/Usage 记录，不能再形成隐藏的次数叠加。保留每次真实请求及失败请求已报告用量，不把重试记为一个虚构请求。
- 语义层的新调用仍由 Loop 按已有规则驱动；partial stream 不跨 attempt 盲目拼接，不执行半截 Tool Call，不重放已发生或 outcome unknown 的工具副作用。取消阻止下一次重试，单次渐进 timeout 与 watchdog 规则保留，不新增 Execution 总期限或自动超时终止。
- 自动审批等其他 consumer 的既定调用策略保留，审批模块不增加应用层重试，不因本题为人工等待设置过期时间。D01/D09/D22 固定请求/流/错误/attempt 契约并验收；模型/Loop/Usage 原文待统一同步，尚未实现。
