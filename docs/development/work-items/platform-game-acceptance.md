## 计分与防止重复计分

计分采用固定分母的二值加权覆盖率。令 `S` 为冻结包中全部可计分叶子项的集合；每项权重为正整数 `w_i`，通过标记为 `p_i`：

```text
W = sum(w_i for i in S)                 # 冻结的完整分母，W > 0
p_i = 1 仅当第 i 项全部验收条件通过且证据有效，否则为 0
N = sum(w_i * p_i for i in S)
coverage = 100 * N / W
coverage_pass = (2 * N >= W)            # 至少 50%，不得靠显示舍入过线
```

复算入口读取冻结清单与验收结果，检查唯一 ID、正整数权重、分母指纹和证据引用，输出 `N`、`W`、精确比值、各系统覆盖率、未通过项与关键门槛结果。输入相同应产生相同结果；缺项、未知 ID、重复 ID、权重不匹配或无效证据不得被静默忽略。最终保存实际命令、工具版本、输入指纹、退出结果和报告，另一执行者能直接复算。

交付一条实际运行通过的复跑命令及环境锁定文件：固定平台与游戏提交、运行时/依赖版本、镜像摘要或等价的精确环境标识、构建参数与测试输入。该入口完成环境校验、构建与可自动执行的验收、证据校验和覆盖率复算；需实际操作的试玩步骤与记录入口一并提供，命令成功不能冒充未执行的试玩通过。当前只规定交付要求，具体命令在 E01 开工时落实，不提前填入未经运行的示例作为证据。

- 未实现、部分实现、失败、未测试、仅口头声明或证据无法定位的项目均计 `0`。如确需拆分行为，只能在冻结清单中先形成独立可观察、独立验收的叶子项；验收时不临时给部分分。
- 权重依据内容与玩法贡献采用统一尺度并写明理由，不依实现容易程度、当前完成情况、代码行数、界面数量或开发耗时调整。同类内容采用一致粒度，不能将易做变体大量拆分来稀释复杂系统。
- 每个可观察内容只归入一个计分叶子项；父级/系统汇总不再计分。跨系统共有机制指定唯一计分归属；复用同一引擎或同一证据可以证明多个不同验收条件，但同一行为、别名、素材变体或同一条目不能重复加分。
- 清单同时保留所有未实现项，完整分母在开发和验收中不随完成情况缩小。各主要系统另报本系统固定分母与覆盖率，不能仅展示全局总分掩盖空缺系统。
- 冻结后若发现原版内容遗漏或错误，保留旧版、原因、来源、差异与影响，经过独立复核后发布新修订并重算全部结果、重跑受影响验收。不能通过删除未完成项、改低其权重或更换参考版本使结果过线；实质目标变更依既有用户决策规则处理。

## 核心玩法与主要系统门槛

加权覆盖率至少 50% 是必要条件。冻结包还必须依据原版确定完整的主要系统集合和核心玩法循环，为每个主要系统列出最低可玩场景、关键行为与跨系统联动要求；这些场景必须全部通过。不得以大量外观、静态物品或界面条目抵消缺失的核心机制，也不得在实现后将未完成系统改称非主要系统。

连续试玩至少证明：从正常新建游戏状态进入核心循环，通过实际交互取得进展并使用已列明的主要系统，保存并退出，再载入继续游玩，且进度与世界状态符合冻结条件。具体操作、输入、预期结果、失败判定及所需时长在冻结包明确；仅能打开页面、查看截图、运行单元测试或孤立展示若干功能不能证明可玩门槛通过。

逐项通过须同时有目标构建与提交、对应验收步骤和实际结果、可定位的日志/录屏/截图或测试产物、平台任务及审核记录。证据应证明该项行为，单张总览截图或一次通用测试不能自动证明全部内容；截图和录屏也不能代替必须执行的交互、持久化与恢复检查。

## 必须通过平台实际组织与执行

使用 D28 验收后的实际运行平台建立游戏 Project，通过平台的 Agent、任务、调度、Execution、Runner、工具与审核能力组织开发。规划、实现、测试、集成与审核应有真实的分工和协作，多 Agent 的任务交接与审核能从平台事实追溯；只在外部开发完成后补录任务、导入日志或展示一段平台截图，不能满足本项要求。

复刻使用自有或已获授权的素材与代码，在产物清单保留来源与授权依据；这不增加许可确认流程。

| 证据类别 | 必须保留的关联 |
| --- | --- |
| 平台与项目 | 实际平台提交/构建、部署与依赖版本、Project 和 Runner 标识、必要的配置记录 |
| 任务与协作 | 冻结清单 ID 到任务的映射、依赖与分工、Agent 身份、实际交接/讨论/返修记录与状态变更 |
| 执行 | Task 到 Execution、Runner/Workspace、实际模型与工具调用、命令、失败及恢复结果的可追溯关系 |
| 审核 | 实现者自测、独立审核者及结论、返修与复测；Task 按平台规则经 `in_review` 后才 `done`，执行成功不自动等于验收通过 |
| 产物 | 代码提交、构建命令、可玩包/访问入口、内容与验收数据、Artifact 标识和内容指纹，能够对应到执行与审核 |

记录保留必要事实并去除凭据；可下载的证据包与持久引用应在停止临时环境后仍可复核。每个计分项目都要能沿“清单 → Task → 协作/Execution → 审核 → 目标产物 → 验收结果”核查，缺少关系的项目不得计为已通过。

机器可读 evidence manifest 固定结构版本，关联清单修订/指纹、环境锁定文件、复跑命令、平台与游戏提交、Task/Agent/Execution/审核标识、逐项验收状态、产物及证据位置与内容指纹、实际检查结果和覆盖率报告。复跑入口检查 manifest 引用的文件与指纹，缺失或不匹配明确失败；不能只给会过期的运行界面链接。

## 实际试玩与平台返修

实现者完成自测后，由独立验证者运行可玩产物，执行冻结的连续试玩与各主要系统场景，并核对游戏构建和证据。记录真实操作环境、输入、步骤、预期与实际结果、问题及复测；不能以文档审查或编译成功代替实际试玩。

在真实组织开发和试玩过程中发现的平台问题，建立可追溯缺陷任务，关联复现步骤、受影响 Execution/日志、对应 D 编号责任模块及验收影响。按平台正式契约修复、按风险独立验证并重跑受影响的平台工作流和游戏验收，通过后将修复提交同步 `main` 并推送；不能只在游戏项目增加旁路、手工改平台数据库或忽略失败来宣布通过。

若平台故障导致其自身无法安排恢复任务，主线程按已有授权恢复平台，并明确记录外部操作、原因与结果；这些操作不能伪称平台内 Execution。恢复后通过平台重跑受影响流程，补齐真实证据。未修复的问题或未通过的复测须保持未完成记录，不能关闭 E01。

## 完成条件与交接

E01 只有同时满足以下条件才标记“已完成”：

1. D28 及全部前置模块已有完整通过证据；E01 使用的实际平台版本可定位。
2. 游戏与参考版本、完整清单、来源覆盖、权重、算法和关键系统门槛已在实现前冻结，并有独立核验；后续修订可追踪。
3. 使用实际平台组织并执行 Agent 协作开发，任务、执行、审核与产物证据完整。
4. 完整分母的加权覆盖率满足 `2 * N >= W`，逐项证据有效，无重复计分；交付环境锁定文件、一条实际通过的复跑命令与完整 evidence manifest，另一执行者按保存的输入得到同一结果。
5. 核心玩法和全部主要系统的冻结门槛通过，实际连续试玩、保存恢复与所需交互验证通过，可玩产物及复现步骤可获取。
6. 实战暴露的平台问题已修复并完成受影响复测；正式代码、说明、证据索引和任务台账已更新，独立可验证的提交已同步 `main` 并推送，记录实际结果。

交接保留当前清单修订与指纹、平台/游戏版本、`N/W` 与关键门槛状态、已通过和未通过项目、真实检查记录、未验证范围、平台缺陷及复测状态、提交与推送结果、未提交文件及明确下一步。未通过完整性核验或尚未试玩时，明确记录对应状态，不能把预计比例或完成声明当作验收结论。
