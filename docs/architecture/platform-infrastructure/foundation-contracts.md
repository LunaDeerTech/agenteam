# 基础契约约定

> 上层：[平台基础设施](README.md)。相关：[仓库结构](../../development/repository-structure.md)、[开发计划 D01](../../development/development-plan.md#d01-固定跨模块契约)。本文固定已确认的共同约束；具体工程类型、服务端口与状态/事务/删除矩阵归位到 [D01 契约基线](../../development/work-items/d01-contracts/README.md)。D01 已通过静态契约验收；这些端口仍待实现与行为验收。

## 1. 身份与时间

- User、Project、Task、Agent、Execution 等持久化对象统一采用 UUIDv7，API 以字符串传输。ID 包含大致创建时间，但不是授权凭据；可读名称与路径不能替代稳定 ID。
- 时间点使用 PostgreSQL `timestamptz`，统一微秒精度；API 返回 UTC RFC 3339 字符串，前端按用户本地时区显示。排序和并发判断由服务端完成，不依赖浏览器保留微秒；持续时长与纯日期字段由对应契约另行定义。

## 2. HTTP 错误与 DTO

HTTP 错误采用 RFC 9457 Problem Details，扩展稳定业务错误码、`request_id` 和字段错误。响应不暴露内部堆栈、Credential 或 Secret；具体字段名、状态码映射和可执行示例由 D01 固定。

HTTP DTO 与内部领域类型分开定义，在所属模块的 HTTP 适配层显式转换。输入只接收允许修改的字段，输出在授权后作安全投影；不直接序列化完整内部对象，不建立容纳全部领域 DTO 的集中包。

## 3. 列表分页

列表统一以稳定排序位置执行游标分页，不提供任意页码跳转承诺。排序必须具有唯一决胜字段；游标须绑定相关筛选与排序条件并经过校验。具体编码、分页大小、失效规则及领域特例由 D01 和领域规格固定；游标本身不保证整个遍历过程的快照一致性。

## 4. 更新版本

可编辑对象读取返回 `version`，适用修改命令提交 `expected_version`；不匹配时拒绝修改，调用方重新读取后决定下一步。前端、Agent Tool 与内部服务使用同一业务语义，不另设 HTTP ETag / If-Match 版本转换要求。

字段类型、适用命令、冲突状态码与事务内推进规则由 D01 / 领域规格明确。已有 Task 命令先解析幂等结果，再校验版本；后台存储维护不能被默认解释为业务版本变化。

## 5. 请求追踪与业务幂等

每次 HTTP 请求具有独立 `request_id`；同一业务操作的重试沿用 `idempotency_key`。同键同语义参数返回原结果，同键不同语义参数拒绝执行，不允许重新执行或静默返回首次结果掩盖冲突。

幂等作用域、参数规范化、并发约束、结果保存期限及 unknown outcome 处理由具体契约固定。旧领域文档中承担幂等含义的 `request_id` 必须在 D01 显式映射，不能把它当作每次传输请求的追踪 ID。重放已创建 Execution 的启动请求仍返回原 Execution，不重新竞争 Agent slot。

## 6. 契约包与模块依赖

跨模块契约按稳定职责建立独立包，由调用方与实现方共同依赖；契约包只包含该边界所需类型和端口，不包含业务实现。避免循环引用、万能 `contracts/shared` 包和大量无必要的细碎空包，具体目录随 D01 依赖矩阵审查后按需建立。

模块通过正式端口访问对方拥有的事实，不直接修改对方表。Runner 不依赖 Central 业务包；双方通信契约仍归 `internal/runnerprotocol`。目录归属见[仓库结构](../../development/repository-structure.md)。

## 7. 事务协调

确需同一数据库事务的跨模块操作，通过统一事务接口协调，相关正式端口显式接收事务上下文。各模块只操作自己拥有的数据，业务契约不依赖具体数据库驱动；仅在需要原子性的边界共享事务，不建立覆盖整个工作流的长事务。

外部请求、邮件和对象存储副作用不属于数据库原子事务，按对应模块的 Outbox、补偿或 reconciliation 契约处理。事务拥有者、锁顺序、错误传播及驱动适配由 D01/D03 和领域规格确定。

## 8. 取消与删除

取消请求持久化后立即返回已接受，后台继续停止；调用方通过查询或实时更新确认最终状态。只有实际停止后才标记 cancelled，重复取消安全，已有副作用不自动回滚。请求断开、超时或“已接受”不能替代停止证据。

对象所属模块发起删除，相关模块通过正式生命周期端口完成引用检查、替换或清理。必要能力未绑定或检查失败时明确拒绝或保持待处理，不宣称删除成功；不以跨模块直接改表或统一数据库级联替代领域规则。取消终态处理、权限、HTTP 映射、删除矩阵、历史引用和事务/补偿边界由 D01 与责任模块规格落实。

Project 的归档及永久删除按[项目生命周期](../project-work-management/README.md#22-project-归档与永久删除)执行；其他领域继续拥有自己的删除和保留规则。

## 9. 领域事件

事件由事实所属模块定义和发布，与业务变更在同一数据库事务写入 Outbox。payload 携带表达事件所需的最小数据：对象 ID、版本、事件类型和必要变更信息；不能只给 ID 再猜测历史变化，也不默认复制完整业务对象。

其他展示数据通过事实所属模块查询接口获取，事件排除 Credential 和 Secret。schema version、去重、乱序与消费者处理由 D01/D06 和领域规格固定。投递与事实存储的边界见 [Internal Domain Events](internal-domain-events.md)。

## 10. 工程基础选择

- HTTP 使用 Go 标准库 `net/http` + `ServeMux`，handler 按模块组织，业务逻辑留在领域服务；WebSocket 等能力另选专用库，不引入 chi 路由依赖。
- PostgreSQL 使用 pgx + 显式 SQL，不以 ORM 自动维护生产表结构。统一事务接口在基础设施层适配驱动，不自动引入 SQL 代码生成依赖。
- 数据库迁移使用 Goose 和一个全局 SQL 序列；常规迁移使用事务，不支持事务的 SQL 须显式标记。锁、失败状态与恢复必须通过真实 PostgreSQL 验证，不承诺库默认行为能安全回滚全部迁移。见[部署迁移](deployment-runtime.md#8-schema-migration)。
- 加密能力优先使用 Go 标准库，缺失能力按需选用 `golang.org/x/crypto` 等成熟专用库并核验版本；不引入 Tink 作为统一框架，不自行发明算法。Secret 加密与密码哈希分别由部署和账号专题拥有。
- 优先把现有环境版本作为依赖候选，兼容性或可用性不满足时更换。审计时记录的候选为 Go 1.27.1、PostgreSQL binary 17.8、pgvector 镜像标签 0.8.1、MinIO RELEASE.2025-09-07T16-13-09Z；这些不是锁定版本，也不证明扩展已加载或集成已验收。固定版本、镜像摘要和兼容性证据由 D02/D03/D05 落实。
- 基础设施集成测试使用独立 PostgreSQL/pgvector/MinIO 测试容器，版本与项目固定版本一致；测试数据、重启、故障注入和资源清理均在隔离环境进行，不使用业务数据。

## 11. 规格与验收边界

上述方向是正式模块设计的共同约束。D01 契约基线承载类型、签名、错误、幂等和删除矩阵，已通过调用方/提供方的静态接口走查；各模块开工前落实数据、事务、并发、恢复与可执行验收。本文不代表这些端口已有实现，不授权生产 stub 或跳过真实集成验证。
