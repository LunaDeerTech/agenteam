## Existing mechanisms and limits

- `tests/security/audit_proxy_test.go:newCommitProxy` reads the actual PostgreSQL simple-query COMMIT. In before mode it withholds that frame and disconnects after release; in after mode it observes the server's `CommandComplete(COMMIT)` and `ReadyForQuery(I)` before withholding both and disconnecting. No Store result is replaced. It is an owned loopback transport fixture with cleanup joining both forwarding goroutines.
- `tests/security/outbound_reload_test.go:newOutboundLateCommitProxy` closes the client after receiving its original COMMIT, retains the original backend transaction, later forwards that same frame, and exposes completion only after the actual server COMMIT/idle frames. Its owned listener, both connections and goroutines retire in cleanup. Existing `TestSecretProjectAuditMutationCommitUnknown` uses this to distinguish returned Unknown from the original writer's still-held locks.
- `internal/central/postgres/transaction.go` supplies the real CommitResult, AttemptID and original cause. A raw Commit transport failure is Unknown unless proven rollback; callback failure and poisoned Tx follow different NotCommitted paths. The follow-up must retain the original returned result and may not synthesize Unknown or infer it from a timeout alone.
- `secret_nonce_test.go:TestSecretNonceUnknownRangeNeverConsumed`, `secret_fence_test.go:TestSecretRotationRealUnknownReconcilesOrRemainsUnknown` and `TestSecretWriteEpochWaitsForOwnedOldWriter` supply existing nonce, maintenance and advisory-lock barrier patterns. They are read-only references, not evidence that the new kind3 paths have run.
- Generic `proxySecret`/`secretOnStore` do not bind `ProjectVariables` or the new native Audit variant. A new test-only constructor must bind the actual Secret/Audit/checker on the same proxy Store with an immutable **controlled** D10 issuer/authority. No old Purpose/Model Lookup path, production stub, late setter, cross-Service prepared handle, or delegated fake Apply/Commit is allowed.

## Concrete final-write sequence

1. Create the real migrated PG fixture. Open an additional real Store through the existing loopback proxy, with the same fixture credentials; only that test transport uses loopback TLS-disabled configuration as the existing fixture requires. Initialize actual bound services with proxy disarmed.
2. Construct the dedicated original typed request, immutable controlled plan and actual prepared handle on that same Secret Service. Preserve safe preparation/locks and the original CommandIdentity cause. Arm only after initialization and all Prepare/nonce transactions have completed.
3. Run one actual `Store.WithinTx` callback: acquire the original full lock union once, call `ApplyProjectVariableWriteInTx`, retain the candidate observation privately, return its actual error. Do not use the convenience fixture's clearing of all uncommitted observations as evidence that the production owner cleared them.
4. At the proxy barrier query durable counts/identities from the direct Store. After-server-commit must have exactly canonical/receipt/payload/native Audit facts; the other two modes must not yet expose them. Keep raw plaintext and secret ciphertext out of logs; comparisons remain inside the test.
5. For pending mode receive actual Unknown while the original backend still owns its transaction. A bounded direct lock attempt must not commit; additionally bind blocking evidence to the original database/backend and required advisory lock. Absence of a receipt at this point is not NotCommitted and grants no retry permission.
6. Release the exact original COMMIT; await actual proxy completion when available, join the original full lock set in a fresh direct transaction, and wait each test goroutine. Before mode must resolve to no durable receipt; after/pending must resolve to the original durable receipt. Check `AttemptID.Validate`, exact original cause and Unknown state without exposing identifiers in logs.
7. Dedicated Lookup/Match must execute in a real caller transaction with full locks and fresh controlled current Session/Project checks. Revoked Session must deny before receipt access. Plans belong to their immutable bound issuer; a prepared object cannot migrate to another Service. A recovery Service uses its own validated plan/prepared handle against the same safe Ref and command, never an interface wrapper around the original handle.
8. Only after original-owner retirement may an explicit test caller recover/reapply the same command. Keep that action visibly outside D04's InTx methods; assert exact receipt/canonical/payload/Audit identities and counts. The test does not assert that a production D10 retry policy exists.

## Maintenance and concurrency details

- Use one actual producer-created kind3 receipt whose Credential was deleted for each maintenance target; the already scheduled 101-row test owns batching evidence. For rotation, complete preparation/nonce work before arming so the intercepted COMMIT is the selected batch, and prove the actual tuple's master version/wrap revision plus persistent processed count at the barrier. `MaintenanceStep` has a real refresh path; `StopAdmission` only after the commit barrier can make that follow-up unavailable without forging a network result.
- Cleanup is different from Audit cleanup reconciliation: current `secret.CleanupProject` calls `commitError` and returns an empty report on Unknown. Do not copy the Audit test's immediate Completed expectation. A later explicit Cleanup call rechecks the current lifecycle gate and scans from the head; restored active/wrong-operation state must deny even if the first deletion committed.
- Concurrent writers use separate real Store/Secret instances and private issuers, never concurrent writes to the shared fixture counters. Each prepares its own handle. For the duplicate-intent case only, bind the same controlled candidate Ref in both plans; differing create Ref is a separate `PreparationRequired` condition, not a duplicate-write failure or permission to replace an original candidate. The formal D10 discovery behavior is not simulated as proven production authorization.
- Hold writer A only after actual Apply/native Audit and before its callback returns. Capture backend identity via SQL in the original transaction; start B with its original locks and use PG blocking evidence instead of a sleep to prove overlap. Default lock timeout remains unchanged; release before it expires. On setup failure release/close and join all goroutines rather than leaving a held callback.
- For stale-version contention use two distinct command keys and the same exact old Credential version; D04's own `loadProjectVariableMetadata`/VersionConflict check is the target. External Variable version is a separate controlled field and is not claimed to be revalidated by a production D10 provider.
- Cross-epoch publication and rewrap-owner-versus-Cleanup contention are additional potential follow-ups, not covered merely by these three writer cases. Existing pure owner-drift/lock checks and generic legacy fence tests must not be relabelled as kind3 real concurrency acceptance.
