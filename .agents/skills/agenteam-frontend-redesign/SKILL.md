# agenteam 前端重设计

本项目编写的编排技能，复用已有设计、实现和验证能力。2026-10-15 将 Impeccable 的 Operate、layout、typeset、critique、polish、animate 方法与公开 AI 前端实践适配为下述工作步骤；来源、固定版本和取舍见[技能来源](../../../docs/development/agent-team/skill-sources.md#前端重设计方法的本地适配)。它不是上游 Impeccable 技能安装，不依赖其命令、检测器、hooks 或二进制。页面规则、尺寸与 token 只在正式设计来源维护。角色、所有权、独立性与 Git 交付沿用[团队流程](../../../docs/development/agent-team/README.md)，不增加阶段审批。

## 触发、输入与来源

适用于重设计规范、完整页面样板、共享控件迁移、业务页面迁移与独立视觉验收。先确认当前任务允许的是规划、样板还是产品实现；读取[设计规范 v2](../../../docs/frontend-design/redesign/target-design.md)、[页面蓝图](../../../docs/frontend-design/redesign/page-blueprints.md)中当前模板，以及[执行计划](../../../docs/frontend-design/redesign/implementation-plan.md)中当前阶段。已有上下文只补读变化，不逐遍加载全部文档。

- 用户已要求对照 Linear 重新制定规范。新规范与其完整页面样板是重设计依据；旧 `styles/`、`layouts/`、现有 CSS token 和 Debug 是待迁移现状，不能以符合旧尺寸、颜色或卡片结构否决新设计。来源优先级与迁移范围见[重设计入口](../../../docs/frontend-design/redesign/README.md)。
- 参考 [Linear 官方产品研究](../../../docs/frontend-design/redesign/linear-reference.md)中的应用界面、官方产品文档与交互；官网营销 hero、渐变或宣传构图不作为工作界面模板。不将公开截图推导成 Linear 官方精确 token。
- 按用户确认的层级解释 **Dashboard → Projects → Workspace → project header menu**：系统首页、项目列表、项目空间及项目内菜单。菜单项、设置分组及其入口逐项对照正式路由与当前产品含义；不得从这条层级描述自行增加导航。Linear 的 Workspace/Team 组织方式不能覆盖本项目的系统、Owner 与 Project 边界。
- 读取本次路由、组件接口、API 与状态来源。权限、Session、请求身份、幂等、Unknown、草稿、取消和恢复继续按业务契约执行；新设计没有授权补造服务能力、搜索、统计或导航入口。
- 用户已否定某版结构或视觉时，先记录拒绝点和待修范围，停止将该版 token、模板和内部通过结论扩散为已接受基准。旧检查只保留其原输入事实；用户反馈、内部审查和真实业务验证分别记录。

## 从一个完整页面建立方法

以下步骤在当前任务或现有设计文档中留下简短决定和可查看结果，不新增永久报告或逐轮审批。授权范围内直接推进；缺少真实产品含义时才合并澄清。

1. **确定工作模式与真实内容合同。** 管理、配置、看板采用工作型界面（Operate）：可预测、便于扫描、信息紧凑而有组织；阅读页补充 Read 的正文与目录要求，不套营销 hero 或装饰卡片。写清用户当前任务、主要对象、主动作、次动作、信息来源、进入/返回与滚动归属。逐项列出本页菜单和设置分组的真实去向、权限、数据字段与命令依赖，用正常有数据、足量中英文、长名称和真实错误构造内容；合成数据明确标注。
2. **把参考图与当前整页放在一起看。** 选与当前任务相近的官方产品参考，实际打开图片，指出要继承的属性，例如导航权重、标题与正文关系、对象到动作距离、成组方式和信息密度；不能只写“像 Linear”。同时实际查看当前实现的整页和同视口截图，区分参考图观察与本项目决定。迁移前后使用相同数据、状态、主题与展开状态；若旧样板没有此页，优先使用当前正式页面，取不到同输入基线时明确来源差异，不能伪称同内容前后对照。
3. **先判断结构，再调整局部。** 暂用中性表面和有限字重，把整页缩小或转为灰阶观察：是否仍能识别主任务、次要信息和主要组？相关项是否靠近，不相关组是否有足够区分？组间与组内间距是否都被同一个值抹平？层级是否只能靠边框、色块或字号撑起？先写出阅读顺序、分组、密度与窄屏变化，再调整布局。没有成立的结构不要继续换色、圆角或阴影。
4. **完成一个可操作的整页。** 先完成当前最能检验结构的一个页面，再推广。包含正常内容、菜单/下拉打开态、当前选择、hover/focus、保存中及明确保存反馈、错误/只读/Unknown、草稿关闭与返回；按真实能力取舍，不补造成功。检查菜单锚定、浮层层级与裁切、键盘/焦点、长文及窄屏滚动。排版按标题、正文、标签、元信息和数据的用途设置角色，依据真实中文/英文行长、行高、字重与缩放调节，不靠装饰字体制造主次。
5. **作者实际看图并批评自己的页面。** 在桌面与窄屏截取完整页面和已打开菜单等关键状态，必须用图像查看能力打开这些截图，再操作完整路径。先写整体判断和影响最大的结构问题，再列局部缺陷；每项指出具体元素、用户影响和修正方向。截图工具成功、DOM 数值正确或文件已生成都不能代替查看图片。按同输入修正并重看，不因一角精致而放过其他区域。
6. **独立审查先看整体，再看检测结果。** 未参与设计/实现的审查者先独立观察完整页面的阅读顺序、分组、比例、密度、排版与参考属性，形成可解释的判断，再结合作者测试、几何、对比度和日志检查遗漏。随后实际打开菜单、移动焦点、修改/保存、关闭/返回、查看失败与恢复。整体结构不成立时明确判为结构返修；不能用局部缺陷清零或技术 PASS 抵销。
7. **结构成立后再 polish 与校准动效。** 区分信息架构/任务流问题、缺失共享规则、局部实现缺陷；分别回到结构、组件或局部修复。对齐、字重、状态色、边界、图标、焦点和动效沿同一完整路径收敛，不把设计方向错误隐藏成“润色”。动效按下节说明因果并实际观察普通模式与 reduced motion。
8. **再提炼与扩散。** 单页完成受影响内部检查后，从已证实的关系提炼语义 token、组件和布局职责；再在项目集合、任务工作台、复杂设置等不同模板中验证适配性，达到当前阶段覆盖后才扩大迁移。未取得用户对返修设计的新认可时，交付写“已修订/内部审查结果，待用户实看反馈”，不称最终设计接受；F1 等产品阶段仍按用户授权和执行计划进入。

## 结构问题与局部缺陷

- 菜单归属错误、设置分组不合用户任务、主次关系模糊、表单/详情载体错误属于结构问题。先修任务路径与区域关系，不以缩间距或加强阴影代替。
- 字体角色漂移、相同控件不一致先判断是否缺少共享规则；真正单点的对齐、裁切、边界或焦点问题才局部修复。
- 用参考图时记录具体图和可观察属性；多张新旧对照不能概括为固定“左新右旧”。不要从宣传配图、检测评分或案例成功描述推导本项目已具备同等质量。

## 动效必须解释状态

每个新增或修订动效先说明触发原因、起始/结束状态、哪些对象移动或改变、为何帮助理解、何时可中断，以及 reduced-motion 替代。常见任务是菜单显隐、对象选择、面板切换、保存受理和结果反馈；不是给所有元素套相同淡入或让用户等待入场表演。

普通模式中实际触发并逐帧或用浏览器动画观察核对：动作发生后何时反馈、过渡是否连续、重复点击/反向关闭能否打断、结束后状态与焦点是否正确。再开 reduced motion 验证空间位移减弱且必要反馈保留；只在 reduced mode 截图不能证明普通动效存在或有质感。优先用现有 CSS/浏览器能力，不为效果擅自增加依赖；精确时长和曲线由完整页面观察后写入正式设计来源，不照抄外部硬值。

## 按模板检查完整页面

以下是检查方法；具体宽度、行高、颜色、断点和路由覆盖以 v2 及当前蓝图为准。

| 模板                 | 必须能在页面中检查的结果                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard / 项目集合 | 当前层级明确；名称、状态和主动作先被看到；列表能横向比较对象；现有数据有合理首屏密度，空态不借假指标填充                        |
| 设置 / 管理          | 栏目导航与表单正文分工清楚；字段按目的成组；保存靠近影响范围；危险区可辨认；复杂实体先选对象再编辑，不常驻堆叠全部新建/编辑表单 |
| 任务 / 资源工作台    | 项目上下文稳定；目录、主内容和属性各有职责；正文占主要空间；选择/打开对象后仍能辨认来源；滚动与窄屏收起不遮挡主动作             |
| 阅读 / 编辑 / 详情   | 正文有适当行宽和空间；元信息退后且可达；保存、关闭、返回与草稿恢复明确；长内容不被全局截断                                      |
| 账号 / 短任务 / 浮层 | 当前任务与必要字段清楚；错误在对应区域；提交中状态可辨；键盘顺序、关闭规则和焦点恢复成立；主要操作在窄屏可达                    |

所有模板同时检查字体层级、对齐、表面与留白、对象与动作的距离。仅换色、缩间距、减边框、统一圆角，或把内容重排成重复卡片，不构成完整重设计。必要的错误、权限原因与 Unknown 不得为了简洁藏入难以发现的折叠区。

## 独立浏览器验收与返修

- 用同一路由、数据、状态、viewport、缩放和 theme 对比迁移前后整页与关键局部；注明浏览器和输入来源。Linear 图用于对照空间/任务模式，不作为跨产品像素相等断言。等待字体、异步状态与必要动画稳定后截图。
- 按当前阶段覆盖浅深主题、桌面/窄屏、长内容、空/加载/失败及适用权限、冲突、Unknown/恢复状态；用真实操作检查键盘、焦点恢复、缩放、reduced motion 与 overflow。执行计划中的矩阵是范围依据，不机械扩大到无关业务全量回归。
- 每项视觉发现写出页面/状态、观察到的问题、对应规范或蓝图、用户影响和修正方向，标明结构问题还是局部缺陷。整体判断先于检测器或测试结果；检测命中是缺陷线索，零命中与技术 PASS 不是设计质量证明。版式门槛失败即返修相应页面；权限、状态或恢复倒退按业务影响处理。作者自查、独立结论与用户反馈分别标注。
- 原 owner 修复后，在相同输入上复验受影响模板与共享层影响范围。相关输入未变的通过结果复用；不得用调整 fixture、放宽断言或删掉失败状态换取通过。浏览器未运行或某状态无法构造时，明确未验证并交负责人处理该范围。

## 简短交付

报告完成的页面/模板与实际文件、依据的 v2/蓝图及稳定输入、工程与浏览器实际结果、截图位置、失败/未验证与下一 owner，并注明停止写入状态。材料沿用任务现有路径和团队保存规则，不另建永久验收档案；规划完成、样板内部检查、用户设计反馈与真实业务完成分别说明。没有用户新认可时不得把内部审查通过写成最终审美接受。
